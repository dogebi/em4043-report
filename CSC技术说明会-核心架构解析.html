Chapter 0

系统总览与架构分层

系统采用「纯 Worker 引擎 + 平台解耦」的架构。Python 引擎（worker-agent-engine）不对外暴露 HTTP，而是通过 Redis Stream 接收任务、Redis Pub/Sub 推送结果；ESM 平台（app/AppAgent）负责会话管理、配置管理与任务投递。二者通过 Redis 与共享数据库协作，实现低耦合、可水平扩展。

图 0 · 总体架构：ESM 平台 ⇄ Redis ⇄ Python Agent 引擎（含独立 Memory / Distill Worker）
📨

纯 Worker / 任务驱动

不依赖 FastAPI，asyncio 直接管理生命周期；外部系统经 XADD 投递任务，Worker 消费执行，结果经 Pub/Sub 实时推送。

🧠

Agent 协同

Master 理解意图、调用工具并规划；Sub 执行专项任务；Audit 阶段审计。支持 DAG 分层并行、取消、暂停/恢复、文件版本。

📚

知识 + 记忆 + 蒸馏

RAG 知识库自动选型、三层记忆（issue/session/user）跨会话增强、知识蒸馏 SOP 流水线，三者构成上下文供给体系。

Chapter 1 · Agent 编排

主/子 Agent、MCP 接入与 SKILL 编排

本章回答「一个 Agent 是如何被配置出来、如何装载、如何调用工具与技能、如何派发子任务」的核心问题。

1.1 主 / 子 / 审计 Agent 分层与协作

系统内置三种 Agent 类型（存于 aigc_work_agents.type），协作关系如下：

图 1 · 主/子/审计 Agent 协作：dispatch_sub_task 是唯一派发通道（不再从回复文本正则解析计划）
🔑
关键设计子 Agent 派发已从「解析回复文本」改为「模型显式调用 dispatch_sub_task 工具」。模型不调用该工具即直接返回最终回答，避免旧兜底机制导致的误派发。子 Agent 配置按 name 加载（load_agent_by_name），继承 Master 的模型凭据。

1.2 LLM 启动装载逻辑（AgentLoader 按需查库）

Agent 配置不在启动时全量加载，而是运行时由 load_agent(agent_id) 在同一个 DB session 内完成 6 条 SQL，返回 AgentSnapshot（AgentConfig + llm_override + tool_names + connectors + skills）。这是整个编排的装载入口：

图 2 · AgentLoader 单次调用 6 条 SQL 的装载链路（工具 = 连接器名；技能 = 摘要列表）

模型凭据三级回退

  • ① 显式 model_config_id（前端可选模型）
  • ② is_default=1 的默认模型
  • ③ 首条记录兜底
  • 解析：aigc_model_detail（model_name / model_params / vision_type）+ aigc_model_supplier（api_endpoint / api_key，RSA 解密）

工具 / 技能来源合并

  • 连接器 = 直接绑定 + Agent 插件 + 项目插件（按 id 去重）
  • 技能 = Agent 直接 + Agent 插件 + 项目插件技能（去重后取摘要）
  • 子 Agent = 关联表 sub_relations ∪ 任务方案阶段 plan_stages.sub_agent_ids（并集去重）

1.3 MCP 工具接入（本地内置 + 远程连接器）

工具统一以 OpenAI Function Calling schema 暴露给模型。工具分为「本地内置（进程内 handler）」与「远程 MCP 连接器（外部服务）」两类，均在装载阶段解析、调用阶段统一路由。

图 3 · MCP 工具接入：本地内置（进程内）+ 远程连接器（懒加载/缓存/前缀路由）
⚙️
工具挂载的「默认 + 用户挂载」引擎每次执行自动注入 AGENT_CORE_TOOL_NAMES（knowledge_search / list_knowledge_bases / report_generate / session_history / request_user_input / todo_manage）作为默认工具；用户挂载工具来自 Agent 直接绑定 + 插件 + 项目插件的连接器（装载阶段解析）。文件工具按 file_driver 与 file_readonly 动态增删（只读模式仅保留 read/list/search）。

1.4 SKILL 技能编排（两阶段：摘要注入 + 按需加载）

技能采用「两阶段」策略控制上下文开销——启动时只注入轻量摘要，模型需要时才拉取完整 SKILL.md：

  1. 第一阶段 · 摘要注入：SkillLoader.load_skill_summaries 只从 aigc_agent_skills 读取 name + description + keywords（每条约 20–50 token），写入 system prompt 的 [可用技能] 段，并提示「用 load_skill_detail 获取详情」。
  2. 第二阶段 · 按需加载：模型判断需要某技能时，调用动态注入的 load_skill_detail 工具 → 按租户路径读取完整 SKILL.md（data/skills/{name}/ 或 data/tenant_skills/{tenant_id}/{name}/）。
  3. 随消息注入：Master 与 Sub Agent 的 prompt 均注入各自关联的技能摘要；技能来源 = Agent 直接 + Agent 插件 + 项目插件（去重）。
💡
为什么两阶段把完整 SKILL.md 全部塞进 system prompt 会快速撑爆上下文、抬高每次 LLM 调用成本。摘要 + 按需拉取让「技能清单常驻、详情即用即取」，在技能数量多时尤为关键。

1.5 项目 / 任务方案中的配置方法

2.2 提示词装配（build_master_prompt）

系统提示词由多段有序拼装而成，统一经 ${} 变量引擎渲染（支持点号嵌套 ${user.name} 与 | 回退 ${a|b}）：

图 5 · Master 提示词装配：8 段 system + user_prompt 三分支渲染

2.3 模型参数加载与优先级

参数来源优先级（高 → 低）

  1. 智能体关联模型参数：agent_model_relations.model_params
  2. 模型详情参数：aigc_model_detail.config_json（装载层已合并进 override_params）
  3. 引擎 ENV 默认值：LLM_DEFAULT_TEMPERATURE=0.5 / MAX_TOKENS=2048 / TOP_P=0.9 / TIMEOUT=600s

实际模型名与凭据必须由数据库配置提供（ENV 默认模型名为空）。支持多模态（vision_type=1）与思考档位（deep_thinking → thinking_budget / reasoning_effort）。

关键运行时控制

  • 流式：默认启用（含工具调用场景），stream_options.include_usage 流末返回 token 用量
  • 退化响应重试：_MASTER_EMPTY_RESPONSE_RETRIES=2，末次降级「无 tools + 强制回答」兜底
  • TTFT / tokens_per_second 记录首字延迟与生成效率
  • 入口净化 sanitize_llm_messages：剔除思考字段，防 Qwen3 系续写空响应
  • 上下文压缩智能体 / 知识库选型可独立配置专用模型与 role（凭据隔离）

2.4 工具挂载与 SKILL 启用流程

Master 在 _build_master_tools 中组装本轮完整工具集，并在有界多轮工具循环中统一路由：

① 本地工具 schema

按 config.tools 从 MCPToolRegistry 取 OpenAI schema（含自动注入的核心工具 + 文件工具）。

② 远程 MCP 工具

get_tools_schema_async 对连接器 list_tools，工具名加 {connector}__ 前缀避免冲突。

③ dispatch_sub_task

有子 Agent 时注入虚拟工具；description 动态列出可用子 Agent，schema 用 enum 约束。

④ load_skill_detail

有技能时注入；模型按需拉取完整 SKILL.md（即 SKILL 启用的触发点）。

🔄
有界多轮工具循环（Master / Sub 一致）每轮带 tools 调 LLM：返回 tool_calls 则逐个执行（注入 _session_id/_messages/_llm_override/_file_driver 等上下文）并把结果追加进对话进入下一轮；无 tool_calls 则该轮即最终回答。Master 上限 8 轮、Sub 上限 5 轮；每轮/每工具前检测取消标记；request_user_input 触发暂停并提前返回。
⚠️
关键澄清 · 本会话能用的 MCP / SKILL 是"限定"的，而非全量项目管理后台里录入的 N 个技能（例如 1000 个）只是一个技能库 / 目录。某个会话真正能调用的，是装载阶段按 Agent + 项目 两个维度解析出来的子集——既不是"后台全部技能"，也不是"某个用户个人偏好"。装配逻辑统一收口在 load_agent() 的 _load_all_skill_ids（技能）与 _load_all_connectors（连接器）。

技能（SKILL）来源 · 三处并集去重：_load_all_skill_ids(agent_id, project_id) 合并下列来源，再经 load_skill_summaries 用 WHERE id IN (…) AND enabled = 1 过滤——只有"被装配 且 已启用"的技能，才会进入 system prompt 的 [可用技能] 段：

① Agent 直接挂载

agent_skill_relations（agent_id）。在 Agent 配置里逐个勾选的技能。

② Agent 关联插件

agent_plugin_relations → plugin_skill_relations。通过插件整包带入的技能。

③ 项目关联插件

有 project_id 时，project_plugin_relations → plugin_skill_relations。让全项目 Agent 共享同一批技能。

连接器 / 远程 MCP 来源 · 同样的三处并集：_load_all_connectors(agent_id, project_id) 按 id 去重合并以下来源，其中 type≠mcp 的作为本地内置工具、type=mcp 的作为远程连接器（惰性连接、按需建连）：

① Agent 直接连接器

agent_connector_relations JOIN connectors（status=1）。Agent 配置里直接绑定的工具 / MCP。

② Agent 插件连接器

agent_plugin_relations → plugin_connector_relations（status=1）。插件包内的连接器。

③ 项目插件连接器

有 project_id 时，project_plugin_relations → plugin_connector_relations（status=1）。

限定维度SKILL 技能连接器 / 远程 MCP
装配维度agent_id + project_idagent_id + project_id
是否与"用户"相关否 · 不按 user_id 过滤否 · 不按 user_id 过滤
是否 = 后台全量否 · 仅并集子集，且 enabled=1否 · 仅并集子集，且 status=1
租户(tenant)仅决定 SKILL.md 读取路径：data/skills/{name}/（全局）或 data/tenant_skills/{tid}/{name}/（租户）；不参与"选哪些技能"。
🎯
对"1000 个技能"的直接回答若项目在技能管理里录了 1000 个技能，并不会让每个用户、每个会话都能用全部 1000 个。实际可用集 = 该会话所用 Agent 直接挂载 ＋ 该 Agent 关联插件 ＋ 该项目关联插件 三者技能之并集，且需 enabled=1。因此：同一 Agent 在同一项目下，所有用户看到的可用技能 / 连接器完全一致；若要给不同角色不同能力，需要配置不同的 Agent（或不同项目 / 插件组合），而不是按用户区分。技能数量本身不拖累系统——第一阶段只注入"名称 + 描述"的轻量摘要（每条约 20–50 token），完整正文仅在模型按需调用 load_skill_detail 时才从磁盘读取。

2.6 记忆助手提取（三层记忆 + 自动提取）

记忆系统采用单表 agent_memories + scope 鉴别列，三层作用域跨会话增强上下文：

scopescope_key场景
issueissue_key工单级记忆，跨会话共享（同一工单多次会话可复用）
sessionsession hash_id会话级记忆
useruser_id用户个人记忆，跨工单/会话（偏好、习惯）

自动提取流程（任务完成后）

  1. 触发：Agent 任务完成后 fire-and-forget；WORKER_MEMORY_PROCESS_COUNT>0 时投递到 stream:memory_tasks 由独立 Memory Worker 消费，否则 inline。
  2. 门控：专用轻量模型（MEMORY_LLM_* 或工作智能体配置）；对话内容 < MEMORY_EXTRACTION_MIN_CHARS=100 跳过。
  3. 提取：LLM 输出结构化 JSON（title / content / keywords / memory_type / importance / scope）。
  4. 去重写入：内容前缀命中已有记忆 → importance += 1；否则 MemoryPG.add（单次上限 5 条）。

检索与增强

  • 多 scope 全文检索（tsvector + GIN 索引），一次查多作用域
  • 检索结果注入 AgentContext.memories → system prompt [记忆参考]
  • MemoryPG 提供 add / search / list_by_scope / update / delete / increment_importance
  • 凭据可来自「记忆提取工作智能体」配置（role 支持 ${} 变量），回退 ENV

Chapter 3 · 扩展梳理

其它重要的核心加载 / 编排实现

除主流程外，以下工程化能力支撑系统在生产环境稳定、可观测、可恢复地运行。

3.1 多进程 Master-Supervisor 架构

图 8 · 多进程 Master-Supervisor：agent / memory / distill 独立子进程 + 崩溃自愈 + 零依赖监控面板

上下文压缩 ContextManager

长对话自动摘要压缩：≤10 条全量保留；11–30 条保留最近 10 条、旧消息 LLM 摘要为 [历史对话摘要]；>30 条取最近 29 条窗口 + 摘要。摘要在 build_master_prompt 中合并进 system，避免被 system 跳过逻辑丢弃。无 LLM 凭据时回退简单截断（每条 200 字符）。

会话消息场景隔离（msg_scope / history_scope）

同一会话用 msg_scope 隔离不同场景：main（主对话）/ audit（审计）/ stage_summary（阶段总结）。history_scope 控制历史读取（缺省 [msg_scope]），main 任务只读 main 历史（修复审计消息混入）；seq_num 跨 scope 统一递增。

同阶段多会话聚合

阶段流转/回退都会新建会话并覆盖 issue.session_id。总结时 PHP 收集兄弟会话（extra_history_sessions），引擎合成 [同阶段前序会话记录] 前情块注入总结上下文，但绝不混入当前会话消息流（避免污染压缩位点计算）。

任务取消 / 暂停 / 恢复 / 撤回

取消：Redis 标记 task_cancel:{sid}（TTL 5min）+ 内存标记，每 2s / 每 5 chunk 检测 → 抛 TaskCancelledError。暂停：request_user_input 存 agent_pause:{id}（TTL 30min）→ 用户提交 → resume_execute 复用占位消息续跑。撤回：归档消息 + 文件版本回滚（rollback_to_parent）。

文件操作 Driver（工作目录 / 版本）

可插拔 local / sftp / ssh 驱动，统一 working_directory 概念；local 用 Git tracker 做版本跟踪与回滚（保留 50 commit），远程用 snapshot（保留 30）。写操作有大小/体积限制，支撑「文件版本」与撤回重答。

审计 / 阶段流转 / 外部集成

Audit Agent 评估阶段完成质量，auto_advance 决定是否自动流转（未通过则暂停待人工）。Jira Webhook → 工单 → 触发 Agent；Zabbix 告警接入。API Key 经 RSA 加解密（与 PHP 侧共用密钥对）。

🔍
可观测性引擎内置零依赖监控面板（标准库 http.server，端口 9100）：HTML 面板 5s 自动刷新 + /api/status JSON 供外部采集；日志按工单号拆分（FULL_REQUEST）；LLM 调用可开 LLM_LOG_FULL_MESSAGES 审计完整请求（默认关）。
